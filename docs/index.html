01 / 怎么提需求

先说结果，
再补约束。

同样是 KV，可能是出图、做方向、反推、评分、拆层，也可能是做视频。入口看你最后要拿到什么。

一条需求，先说清 结果、用途、硬约束、素材职责、交付形式。

1

我要什么

图片、视频、PSD、HTML、Markdown、Prompt，或只做到某一步。

2

用来干什么

例如转化、角色记忆、玩法证明、活动传播、研究决策。

3

什么不能改

角色、Logo、玩法事实、尺寸、语言、禁用元素，以及每份素材的职责。

需求里不用写：内部命令、Skill 名、API 字段。

10 / 常见说法修正
把模糊词，
换成可执行条件。

        
下面这些说法最容易让结果跑偏。

      

      

        
“做个高级感 KV。”
→ “做角色危机型 KV：第一眼看到人物困境，第二眼看到唯一逃生目标。”

        
“参考这些图综合一下。”
→ “图1锁角色，图2借空间，图3借色光。”

        
“给我 10 张 KV。”
→ “先做 10 个方向，只生成前 3 个验证图。” 或 “直接生成 10 张正式成图。”

        
“把这张 KV 做成视频。”
→ “只要微动画 + Seedance Prompt。” 或 “最终交付视频文件。”

        
“分析竞品。”
→ “研究市场表现。” 或 “研究竞品视觉，并转成当前项目可用的包装方向。”

        
每次返修都新建需求。
→ “返修刚交付的第 1 版，只改标题区和 Logo 安全距离，其他保持。”

        
所有参考图都当项目事实。
→ 外部参考只学方法；批准的自有产出再登记为 historical-project-output。

        
API 返回成功就结束。
→ 继续看候选、做 Final Review、Manifest 和 Promote。

      


      

        

          
技术细节

          
需要时再看

          
路由看哪里？
.agents/lib/request_routing.py 定义 request_type → primary_skill；图片生产类同时绑定 production_branch。

          
request 目录怎么分？
request.md 记录需求；input/ 放输入；work/ 放过程文件；output/ 放 Promote 后的正式版本；state.json 记录状态和 revision。

          
下一步怎么判断？
Primary Skill 根据当前 artifacts 和 gates 继续。

          
哪些视觉任务会检查 Baseline？
系统按当前入口的视觉要求自动判断。必须依赖项目视觉事实的任务会检查；可选任务只在已经绑定 Baseline 时检查；无关任务不会被阻断。
